# Agent Contract

Implementation: `orchestrator/src/main/java/com/agentic/orchestrator/agent/` and
`service/AgentExecutionService.java`.

## Principle

Agents are untrusted workers. They receive an `AgentRequest`, return an `AgentResponse`, and never touch
task state. The Orchestrator validates the response and decides the state change.

## Interface

```java
public interface Agent {
    AgentRole role();
    AgentResponse execute(AgentRequest request);
}
```

## Request

| Field | Description |
|-------|-------------|
| `executionId` | Unique id of this execution, generated by the Orchestrator |
| `agent` | Role the request is addressed to |
| `task` | Immutable snapshot of the task (includes current status) |
| `inputs` | Extra key/value context (e.g. SA design for BE) |

## Response

| Field | Description |
|-------|-------------|
| `executionId`, `agent`, `taskId` | Must echo the request |
| `status` | `COMPLETED`, `FAILED`, `NEEDS_INPUT`, `BLOCKED`, `CHANGES_REQUESTED` |
| `result` | Required for `COMPLETED` / `CHANGES_REQUESTED`, otherwise null |
| `error` | `AgentError(code, message)`; required for `FAILED` / `NEEDS_INPUT` / `BLOCKED`, otherwise null |

## Result schemas

| Schema | Fields | Rules |
|--------|--------|-------|
| `DesignResult` (SA analysis) | `summary`, `tasks: ProposedTask[]`, `risks` | summary not blank; ≥1 task; each task has title, type, priority, ≥1 acceptance criterion |
| `ImplementationResult` (BE/FE) | `summary`, `branch`, `pullRequest?`, `changedFiles` | summary and branch not blank; ≥1 changed file |
| `ReviewResult` (SA review) | `summary`, `comments: ReviewComment(file, severity, message)[]` | `CHANGES_REQUESTED` needs ≥1 comment; an approval (`COMPLETED`) must not contain `BLOCKER` comments |

## Agent workflow policy

| Task state | Allowed agents | Expected result | On `COMPLETED` |
|------------|----------------|-----------------|----------------|
| `BACKLOG` | SA | `DesignResult` | no transition (task creation from design comes in Phase 3) |
| `IN_PROGRESS` | BE, FE | `ImplementationResult` | → `CODE_REVIEW` |
| `CODE_REVIEW` | SA | `ReviewResult` | → `MERGED` (real merge added in Phase 6) |

Any other state/agent combination is rejected with `AgentNotAllowedException` before the agent runs.

## Execution lifecycle

1. Load the task; reject if the agent is not allowed in the current state.
2. Build `AgentRequest` with a new `executionId`.
3. Run the agent. An exception becomes a `FAILED` response with code `AGENT_EXCEPTION`.
4. Validate the response. Any violation replaces it with a `FAILED` response, code `INVALID_RESPONSE`,
   listing all violations.
5. Apply the outcome through `TaskService`:
   - `COMPLETED` → the policy's transition, if any
   - `CHANGES_REQUESTED` → `CHANGES_REQUESTED` (retry limits apply, may result in `BLOCKED`)
   - `BLOCKED` → block the task with the agent's message (if the state is blockable)
   - `FAILED`, `NEEDS_INPUT` → no state change
6. Return an `AgentExecution` audit record: ids, timestamps, effective response, violations,
   state before/after.

## Not yet covered

- JSON (de)serialization of responses from LLMs (Phase 3).
- Automatic retry of failed/invalid executions.
- Persisting `AgentExecution` records (observability).
- Tool permissions per agent (Phase 4+).
